# 科研泛化路线图（前瞻规划）

> **状态**: 前瞻规划（Not Started）— 仅作设计约束预留，不作为当前工作重点
> **前置条件**: Agent OS 在代码领域达到最小可运行完备单元（MVP 完备）后启动
> **日期**: 2026-08-05

## 1. 背景与定位

Praxis 当前专注代码领域（五层 Agent OS：kernel → shell → cell → bridge → user）。
本文档是代码领域完备**之后**的泛化目标——特别是科研场景。

**核心判断**：Praxis 的架构对科研有结构性优势——代码领域打磨出的
memory/archive/convention/sandbox/演化机制，恰好是科研最稀缺的能力
（可复现、对抗评审、阴性结果保留、自我演化）。

**注意**：科研泛化 ≠ 科研技能库（社区已有 scientific-agent-skills 等
158+ 流程封装，属"生产型技能"）。差异化机会在**创新底座**（见 §4）。

## 2. 代码 vs 科研的本质差异

| 维度 | 代码领域（现状） | 科研领域（目标） | 影响 |
|------|------------------|------------------|------|
| 验证器 | 编译/测试/lint（快、客观、自动） | 实验/审稿（慢、主观、人工） | 需替代验证闭环 |
| 错误成本 | 低（git 可逆） | 高（实验不可逆） | 需假设前置审查 |
| 问题形态 | 已定义（任务→实现） | 开放（什么问题值得问？） | 需问题生成能力 |
| 时间尺度 | 分钟-小时 | 天-周（实验周期） | 长周期任务状态机 |
| 知识沉淀 | 代码即文档 | 阴性结果通常不发表（浪费） | **阴性保留是 Agent OS 独有机会** |

## 4. 创新底座（差异化机会，科研形态）

| 机制 | 科研形态 | 差距 |
|------|----------|------|
| 假设管理 | R5 图 hypothesis 节点 + evidence 边（supports/refutes） | 需扩展图语义（现仅 contradicts/depends_on）|
| 平行假说 | 多 agent 各自持假说 → Convention 对抗 + 少数派保护 | 需少数派奖励规则 |
| 探索角色 | 专职"质疑者"：挑战主流假设、生成反直觉问题 | 需 explorer 角色 + 探索豁免 |
| 阴性知识库 | 失败实验 → lean case → 下次避免 | ✅ 已具备（lean traces）|
| 探索预算 | 独立 token/时间配额（非推理预算）| 需新预算类型 |

## 5. 三阶段路线图

```
Phase 1（代码域内验证）: explorer 角色原型
    - 质疑任务假设 / 生成替代方案 / 探索豁免（失败不扣声誉）
    - 产出注入 R5 图（供未来"意外连接"）
    - 在代码域检验机制（验证器闭环存在，可安全实验）
        ↓ 机制成熟
Phase 2（科研骨架）:
    - protocol 技能（生产型，可导入社区）
    - 实验 Card 类型 + 长周期任务状态机（挂起等待实验）
    - 数据归档规范（原始数据不可变 + 分析可复现）
    - R5 假设语义（hypothesis/evidence 边）
        ↓ 工作流打通
Phase 3（科研闭环）:
    - 假设驱动循环: hypothesis(explorer) → experiment(subagent)
      → evidence(R4 + lean) → revision(R5 refutes 边) → 下一轮
    - 多 agent 科研团队: PI(统筹) + domain experts + skeptic(对抗)
    - 科研工具面（MCP 接文献/仪器/数据分析）
```
