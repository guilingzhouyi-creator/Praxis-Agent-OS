## 3. 补充发现（报告未覆盖）

### 3.1 🟡 `api_gateway.py` `_Handler` 内部类 397 行过长

`api_gateway.py` 中定义的内部类 `_Handler`（继承 `BaseHTTPRequestHandler`）实际处理 HTTP 路由。397 行放在 `api_gateway.py` 内，而不是分离到 `api/_handler.py`。与 `api_handlers/__init__.py` 的 835 行呈互补性超重。

### 3.2 🟡 `llm_providers.py` 探测机制在每次 `capabilities()` 时执行真实 LLM 调用

```python
# L76-88
try:
    self.generate("ping", reasoning_effort="low", max_tokens=1)
    caps.add("reasoning_effort")
except Exception:
    logger.debug("llm_providers: reasoning_effort probe failed")
```

每次调用 `capabilities()` 都执行真实的 LLM API 调用（"ping"）。这产生了不必要的 API 调用开销。探测结果应缓存。

### 3.3 🟡 `mcp_bridge.py` MCP 服务器启动使用 `shell=True`

```python
_subprocess.Popen(cmd, shell=True, ...)
```

通过 `shell=True` 执行字符串命令，存在命令注入风险（虽然命令由配置控制）。

### 3.4 ℹ️ `sandbox/cell_sandbox.py` 997 行 — L4 最大文件

与 L3 的 `cell/__init__.py`（1091 行）和 L2 的 `commands.py`（1335 行）形成模式：每层都有一个单文件超过千行。

| 层 | 最大文件 | 行数 |
|----|---------|------|
| L1 | `bus.py` | **426** |
| L2 | `commands.py` | **1,335** |
| L3 | `cell/__init__.py` | **1,091** |
| L4 | `cell_sandbox.py` | **997** |

> **模式**: L2/L3/L4 各有一个 1,000± 行的"巨无霸"文件。建议系统性治理。

## 5. 跨层问题追踪

### 5.1 DCLP 模式缺失：L4 最严重，L2 次之

| 层 | 无锁单例数 | 修复难度 |
|----|-----------|---------|
| L2 | 3 | 🔵 易（5 分钟） |
| L4 | **14** | 🔴 中（20 分钟） |
| L1 | **0** ✅ | — |
| L3 | **0** ✅ | — |

L4 层的无锁 DCLP 问题是 **所有层中最严重的并发安全问题**。L1 和 L3 都做到 100% 正确，L4 这一缺口需要系统性修复。

### 5.2 `except Exception:` 模式：L3/L4 最重

```
L1: ~36 处     (中度)
L2: ~20 处     (轻度，代码量最小)
L3: ~70+ 处    (重度)
L4: ~80+ 处    (最重)
```

L4 的 80+ 处宽泛 except 中，模式 A（无声吞没）比其他层多一些。

### 5.3 L2→L4 直连依赖的风险

`docs/l2-code-review.md` 发现 L2 有 5 处 `from l4.*` 导入。如果 L4 按照本报告建议重构（如拆分 `api_handlers/__init__.py`），L2 的这些导入会断裂。这与 L2→L3 私有属性访问问题（13 处）同属**跨层耦合债务**。

### 5.4 测试缺口：L4 最严重

| 层 | 测试/源码比 | 核心未测试模块数 |
|----|------------|---------------|
| L1 | — | — |
| L2 | **1.1x**（~85 测试） | 少数 |
| L3 | — | 较多 |
| L4 | **<0.1x**（8 测试 / 58 文件） | **~40 个** |

L4 的测试覆盖是四层中最弱的。信用凭证库（`credential_vault.py`）、LSP、Sandbox、MCP 桥接等敏感模块**零测试覆盖**。
